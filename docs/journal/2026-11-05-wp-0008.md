# WP-0008: Promo codes: "first event only" flag enforced per host

- **Author:** API Annie (Backend Developer (Python/Flask))
- **Date:** 2026-11-05
- **Branch:** wp-0008-promo-codes-first-event-only-flag-enforc

## Summary

Addressed the QA finding: the first-event-only check now survives reaping. db.py adds an idempotent `promo_redemptions` table (id, email lower-cased, code, meet_token, created_at, plus an index on (email, code)) with no foreign keys. host_redeem calls the new `_record_redemption` after each successful consume, using the meet's owner_email. `_first_event_violation` checks that table first (excluding the current meet), then still runs the earlier meet scan, which covers redemptions made before the table existed. reap.py needs no change. `reap_web_events` only deletes by meet id (via `_purge_meet`) and by owner user id (sessions and users), so it never touches the new table. Test case 5 runs the real `reap_web_events`: host C redeems, the meet and user are deleted, C signs up again with the same email and creates a new meet, and the redeem is rejected with the friendly error, `used_count` unchanged. Cases 1-4 still pass. Verify: `python3 -m py_compile road.py db.py app.py reap.py`, then `/tmp/wp8venv/bin/python scripts/test_promo_first_event.py` (or any Python with requirements.txt installed). It prints PASS 1-5 and exits 0; it also runs `init_db()` twice for migration idempotency. Files changed: db.py, road.py, app.py (version bump from the earlier round), scripts/test_promo_first_event.py. Nothing committed or deployed.

## Where the agent was wrong

The first round only scanned existing meets, so reaping defeated the check. My first fix for it also failed: I excluded the current meet by meet_id, but SQLite reuses the top rowid after a reap. In test case 5 the new meet got the reaped meet's id, so the old redemption row was wrongly excluded and the code was accepted. I fixed it by keying the "same event retry" exclusion on meets.public_token, which is random and never reused. This could have bitten production too.

## Dead ends

Using meet_id as the log's exclusion key (see above). The reaped host's login is deleted, so the user id can't be the key. The email comes from the meet's owner_email, and the log is keyed only on email and code.

## Judgment calls

The key is the lower-cased, stripped owner_email plus the code. I record a row for every successful consume, flagged or not; only flagged codes are ever checked. The check runs before consume and rejects if an email+code row exists for a different meet_token. A partial-percent code that was consumed but not yet paid can be retried on the same meet. A host who abandons an unpaid partial-discount checkout and later creates a second event would be blocked, which is arguably correct for a one-per-host code. reap.py was NOT modified (nothing to protect, as explained above); the Boss asked me to note any reap.py change here, and there is none. The old meet scan stays as a fallback. The check and the consume still aren't atomic across concurrent requests (low risk, previously noted). A different email address defeats this, as with any email-keyed limit.
