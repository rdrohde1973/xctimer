# WP-0008: Promo codes: "first event only" flag enforced per host

- **Author:** API Annie (Backend Developer (Python/Flask))
- **Date:** 2026-11-05
- **Branch:** wp-0008-promo-codes-first-event-only-flag-enforc

## Summary

Added optional promo_codes.first_event_only (idempotent migration in db.py, default 0). Admin form on /organizers has a "First event only" checkbox, and the codes table has a new "Scope" column. host_redeem now calls the new read-only _first_event_violation(code, mid) BEFORE _consume_promo. For a first_event_only code, if the host already has another paid/published event, it returns 400 {"error":"This code is for your first event only."} and used_count is untouched. Existing codes are unaffected (flag defaults 0). Version bumped to 1.107.0-promo-first-event-only (app.py APP_VERSION). Files: road.py, db.py, app.py, scripts/test_promo_first_event.py (new). Verify: `python3 -m py_compile road.py db.py app.py`, then `<python with requirements.txt installed> scripts/test_promo_first_event.py` (temp DB, exits 0, prints PASS 1-4 for the four acceptance cases; it also runs init_db() twice to check the migration is idempotent). I ran it in a throwaway venv at /tmp/wp8venv (pip install -r requirements.txt); the system python has no Flask. Not deployed; nothing committed.

## Judgment calls

Ownership key = owner_user_id in the meet's settings_json, with owner_email as fallback. /host (host_create) puts every self-serve host's meets under ONE shared organizer ('XCTimer Web'), so organizer_id can't tell hosts apart; users.email is globally unique and one host = one user, so user id and email are the same identity. "Published or paid" = settings host_paid true (host_publish, _mark_host_paid and free promo redemption all set it). "Other" event = any meet with a different id. Rejection is HTTP 400 JSON in the existing error shape, which the front-end alert() already shows. Inactive/unknown codes fall through to the existing "not valid" message. Version bumped to 1.107.0 (minor, new feature). Known limitation: check-then-consume isn't atomic across two simultaneous requests from the same host (low risk). The check scans all meets' settings_json in Python, which is fine at current scale.
